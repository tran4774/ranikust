## 2. Security posture

The core confinement held everywhere the hunters looked:
- `RootPath` with `openat2(RESOLVE_IN_ROOT|NO_MAGICLINKS)`, plus pinning with `NO_SYMLINKS|NO_XDEV`;
- descriptor-based deletion that never crosses a mount;
- the layer type allowlist and whiteout handling;
- digest, size and diff_id checks;
- credentials withheld over plain HTTP and unverified TLS on `/`;
- the Direct-mode capability trim and process sweep;
- the state-directory ownership chain;
- the kaniko walk's pin-check-reopen discipline.

The most serious lead is new in this run. **A possible Full-sandbox escape of the runc CVE-2024-21626 kind (lead 1).** The RUN child keeps ranikust's directory descriptors (no CLONE_FILES) and calls chdir(WORKDIR) and execve by plain path after /proc is mounted and before descriptors are closed. A WORKDIR, inherited image WorkingDir or PATH entry of `/proc/self/fd/<n>` passes validation, so the RUN may start with its working directory outside the root. It is source-only and needs the VM run in its plan before anything else.

The other leads cluster in seven places:
1. **Second lookups by name inside the Full sandbox's set-up.** Two of them would bypass T17 (`/proc` masks) and T18 (`nodev` on cache binds) if the kernel behaves as inferred.
2. **ranikust acting with more authority than the RUN in kaniko mode on `/`.** Retained capabilities, and a `--secret` reopened per RUN.
3. **Operator-typed host paths followed through context-owned symlinks as root.** This covers `--dockerfile`, `--context` and the output writers, plus context files read as root without a link-count check. Whether this counts depends on one maintainer ruling: is the build-context owner a principal distinct from the operator?
4. **A credential misdirection to Docker Hub.** It happens for an upper-case, dot-less registry name, because `rnk_oci` and `oci-spec` disagree. Separately, a Dockerfile-named registry can make ranikust's own anonymous token-realm fetch reach any URL, which `--network=none` does not cover.
5. **A state volume shared between kaniko mode on `/` and other builds.** A Direct RUN can write it, and later builds trust what it planted (store entries, roots, journals).
6. **A family of unbounded allocations and waits that contradict T15.** These are tar extension headers, manifest/token/config bodies, the kaniko created-path set, deep-tree deletion, and the registry read timeout that holds the shared store's per-digest lock.
7. **The repository's own agent automation.** The allowlist in `.claude/settings.json` lets `just test`/`just changelog` run arbitrary shell commands, and allows `cargo`/`git` options that bypass the deny list.

## 5. What the maintainer needs to decide

- **Lead 1 first.** Run its VM plan (dummy canaries) before any other hardening. The fix shape is known: close every inherited descriptor the child does not need before any path lookup, resolve WORKDIR with `openat2(RESOLVE_IN_ROOT|RESOLVE_NO_MAGICLINKS)` and `fchdir`, refuse `/proc/` and `/dev/fd/` spellings in WORKDIR and argv[0] candidates, and check the cwd after the switch. Add it as a T2 red-team test.
- **Is the build-context owner a distinct, lower-trust principal?** Threat-model section 3 (line 43) treats context *content* as hostile but trusts operator *paths* (line 42). Leads 6, 11, 12 and 13 turn on this ruling. If the answer is yes, one fix pattern closes the family: resolve operator paths beneath their parent with `RESOLVE_NO_SYMLINKS`, open outputs with `O_NOFOLLOW`, and refuse output paths inside the context.
- **One state volume shared with kaniko mode on `/` (leads 7, 8, 9).** kaniko mode on `/` accepts a marked persistent state directory with only a warning, and `Store::open` never takes the anonymous store's lock, so a Direct RUN can plant or change what later or concurrent overlay and per-stage builds trust: published entries, in-progress roots and uppers, and journals that replay opens as root without `O_NONBLOCK` or a file-type check. Either refuse a persistent state directory in kaniko mode on `/` (or take one lock both opens honour), and harden journal replay like `lock.rs`. ADR-0056 and the book say a second build on a state directory in use is refused; that is not what the code does.
- **Direct mode authority (leads 4, 5).** ranikust keeps capabilities that it trims from the RUN, and it follows RUN-writable names afterwards. One option is to drop ranikust's own extra capabilities before the first RUN. The other is to pin every operator path by descriptor before any RUN.
- **T15 budgets (leads 16–22).** Q-056 defers the tar header bound, but T15 promises clean failure. Decide caps for PAX/GNU headers, manifest/token/config bodies, entry and path depth, and a registry read deadline. The read deadline matters most, because a stalled pull holds the shared store's lock.
- **Threat-model and doc updates the verifiers asked for, even where they rejected a candidate:**
  - section 6 should name AF_VSOCK/AF_ALG and unprivileged user-namespace creation by a default RUN (no default seccomp until Phase 3);
  - section 6 should name the same-uid host account's reach into a non-root RUN until `--userns`;
  - `sandbox.md` claims CLONE_NEWUSER is added, but it is not;
  - ADR-0047's wording on setuid across namespaces is wrong;
  - `--registry-certificate` should never point into an untrusted context;
  - `workflow.md` still says `git commit`/`cargo run` ask, but the `ask` list is empty since 06d5f7b.
- **Registry realm under `--network=none` (lead 25).** ranikust's own token-realm fetch follows any URL and redirect a Dockerfile-named registry gives, from ranikust's network namespace. Either restrict anonymous realms and redirects (scheme, host, no private ranges), or state in threat-model section 6 that `--network=none` covers RUN only, not ranikust's own registry traffic.
- **Agent tooling (leads 26, 27).** Quote `{{ args }}` (`-- "$@"`) in the `test` and `changelog` recipes, and narrow or remove the `cargo *`/`git *`/`rg *` prefix rules. Whether this matters for your own sessions depends on the permission mode they run in. That is an owner-observed fact, so this run did not establish it.

## 8. Positive patterns worth keeping

- **Path confinement:** every untrusted path goes through `RootPath`. Hunters found no `std::fs`/`Path::join` on an image or context path in product code.
- **Deletion and the root:** deletion walks by descriptor, compares `mnt_id`, and refuses the machine's own root. Red-team tests already cover concurrent swaps.
- **Blob integrity:** blobs and layers are size-bounded while they stream, then checked by digest and diff_id before publication. On `/`, streamed layers are spooled and verified before extraction.
- **Credentials:** they are withheld from plain HTTP unless the operator typed the registry. On `/` they are also withheld from unverified TLS. reqwest strips Authorization across hosts, and oci-client does not forward it.
- **Process hygiene:** PR_SET_DUMPABLE 0 and RLIMIT_CORE 0 come first in `main`. The child does nothing async-signal-unsafe between clone and exec. All fds are CLOEXEC. PDEATHSIG is re-armed after the uid switch. The sweep uses pidfds and fails closed.
- **Refusal order:** the kaniko-on-`/` refusals run before any write. Every mode fallback is to a stronger or equal isolation.

## Appendix A. Hardening notes by subsystem (verbatim from hunters; not findings)

### crates/ranikust

- crates/ranikust/src/build.rs:399 + crates/rnk-context/src/source.rs:204-235: for an in-context Dockerfile, <Dockerfile>.dockerignore is opened at context.origin().join(rel). O_NOFOLLOW refuses only the final component, so a context-owned directory symlink in rel resolves on the host. Only files named '<basename>.dockerignore' are reachable and they only filter a context the same owner controls, so there is no finding. Still, it breaks rules.md:21 and the claim at docs/agents/crates/rnk-context.md:142-144. ### crates/rnk-layer

- rnk-layer header.rs to_ascii (line 244) drops non-ASCII bytes and NULs to build the ustar fallback name and linkname. A component such as '.\xff.', which EntryPath accepts and RUN can create, becomes '..' in the ustar field. PAX-aware readers (Go archive/tar, so containerd/Docker, plus GNU tar and the tar crate) use the exact PAX path, and Go's writer behaves the same way, so this matches the baseline. To be robust against PAX-unaware readers, write an inert ustar name, for example the PaxHeaders-style name or a hash, whenever the ASCII projection would differ from the real name in any component.
- Nothing caps a base layer's decompressed size (decoder.rs). Disk use under --state-dir (overlay mode) or on the container's / (kaniko mode) is bounded only by free space. This matches T15's 'fail cleanly on exhaustion': Store::fill removes the temporary entry on error (store.rs:680,693), and an OOM kill or crash leaves it for the next start-up cleanup. An optional cap on tar bytes per layer, or a ratio check of decompressed against compressed size, would bound shared-disk use for builds in multi-tenant runners.
- Each concurrent zstd decode may allocate up to a 128 MiB window (libzstd default), on top of tar-crate buffers. The peer-owned rnk-sched memory admission should count extraction memory per concurrent base-layer pull, not only RUN.

- In kaniko mode with per-stage directories, the directory descriptors open at a RUN clone are open-ended: the state, context, stages and stage-directory holds; parents kept for later readers; concurrent stages' extraction, copy, prune and walker pools; and the release thread's delete_contents. The fix should therefore close everything in the child by default (close_range over the gaps between the descriptors the child needs: error pipe, ParentCheck stat, netns, stdio sources, script memfd) rather than mark particular holders. unshare(CLONE_FILES) in the spawner thread alone would not suffice, because Store.state and the build lock are open before the spawner starts.
- threat-model.md T12 relies on the full sandbox to keep parallel stages apart in kaniko mode with mounts, but no test checks that a RUN cannot reach a sibling stage directory or a parent kept for COPY --from. A T2 VM test listing reachable stage directories from inside a RUN would document this invariant after the fix.
- /proc/self/exe as argv[0], or as a #! interpreter, of a full-sandbox RUN names the host ranikust binary (the child's mm keeps it until execve), so ranikust's binary executes inside the RUN. No write path to it was found in source: ranikust's long-lived process keeps the binary deny-write (ETXTBSY on current mainline kernels), the RUN's new PID namespace holds no other ranikust process, and ranikust is non-dumpable (main.rs:101). runc answers this with a sealed memfd copy of its binary. A T2 check of ETXTBSY on the supported kernels would settle it.
- threat-model.md T7 and design/sandbox.md step 8 describe only descriptors that survive execve. They should also require that no inherited descriptor is reachable through /proc/self/fd while the child resolves WORKDIR and the exec candidates.
- Isolation::Direct with chroot mounts no /proc, so the magic-link route does not exist there. Direct on '/' inherits anonymous-store descriptors that are files, which chdir refuses. No reach was found in either; both are another lifecycle and were not pursued further.
- crates/rnk-sandbox/src/child.rs switch_user_and_exec: call prctl(PR_SET_DUMPABLE, 0) right after set_thread_res_uid. The child is a CLONE_VM-less copy of ranikust (spawner.rs:360-363) holding ranikust's environment and heap until execve; setresuid sets dumpable to fs.suid_dumpable, so with suid_dumpable=1 a same-uid host user could read that copy in the pre-exec window. execve resets the flag for the RUN anyway, so the call costs nothing.
- docs/adr/0047-kaniko-workdir-chain-is-private.md:64-69 says a setuid-root file reached through /proc/<pid>/root 'then works'. In Full mode the path lands on a mount of the RUN's private mount namespace, which the kernel treats as nosuid for a process in another mount namespace (mnt_may_suid/check_mnt), and a hardlink out fails with EXDEV. Verify this in the VM; if it holds, correct the consequence in the threat model rather than rewrite the accepted ADR.
- Full mode has no counterpart of sweep::warn_ptrace_scope. With kernel.yama.ptrace_scope=0 (the Debian and Fedora default), a same-uid host process can PTRACE_ATTACH to a non-root RUN and change what it writes into the image. A warning when the Dockerfile has a non-root USER would document this.
- hidepid on the host /proc does not mitigate this: it still admits processes that pass ptrace_may_access(READ), so it should not be suggested as an operator mitigation for same-uid access.
- crates/rnk-builder/src/mounts.rs:50-58,75-80 (Direct mode on /): a file --secret is re-opened by path at every RUN that mounts it, following symlinks, with ranikust's privileges. An earlier root RUN can replace the src path (or a writable parent such as a /var/run symlink) with a symlink to /proc/self/maps, /proc/self/fd/<n> (anonymous store files, numbers listable in /proc/<ranikust>/fd) or, in a container given extra caps such as SYS_PTRACE, /proc/<pid>/{fd,root,cwd}/... of processes the RUN itself cannot ptrace; a later RUN with --mount=type=secret,id=<id>,env=X then receives the content. Only NUL-free regular files <= 500 KiB pass (environ and compressed/tar blobs are stopped by the NUL check at mounts.rs:404, which exists for another reason). Fix: in Direct mode read file secrets once at start-up into memory (or keep the descriptor opened by Secret::check) and open with O_NOFOLLOW/openat2 RESOLVE_NO_MAGICLINKS; regression: a Direct T2c test that swaps the src for a symlink to /proc/self/maps between two RUNs and expects a refusal.
- crates/rnk-sandbox/src/sweep.rs:94,137 compare ppid values read from /proc with rustix getpid(), while spawner.rs:296-309 (ParentPid) deliberately reads /proc/self/stat because /proc may number pids in an outer PID namespace. Where those differ, children_of_self and run_tree find nothing and kill_run_tree returns Ok, so the B6 sweep fails open silently (and, if ranikust is pid 1 inside, could match unrelated outer processes). Only reachable through unusual operator set-ups (a PID namespace without a matching /proc, then CAP_SYS_ADMIN dropped). Fix: use ParentPid (or refuse start_direct) when /proc/self/stat's pid differs from getpid().
- crates/rnk-sandbox/src/sweep.rs:54-71,140-145: the loop ends on the first /proc snapshot whose tree is empty. A RUN process that forks and exits continuously, with the pid counter wrapping inside one readdir window (new pid below the iterator, old one gone before it), is absent from that snapshot and survives. Theoretical race with low impact (ranikust stays non-dumpable; survivors gain nothing a RUN lacks except timing during walk/push). Hardening: require two consecutive empty snapshots, or a cgroup of the RUN where one can be made (ADR-0051 mentions it).
- crates/rnk-sandbox/src/spawner.rs:2455-2467: the T2 test a_direct_run_on_slash_keeps_only_dockers_capabilities asserts CapBnd only; CapPrm/CapEff/CapInh/CapAmb of the RUN (which trim_capabilities sets) are not asserted, so a regression in trim_capabilities would pass it.
- Same root cause as rnk-sandbox/child.rs:switch-user-and-exec:pre-exec-path-lookup-through-inherited-fd-magic-links (peer unit, Isolation::Full). Under Isolation::Direct on / it reaches no ADR-0051/0056 state today. chdir(args.workdir) at child.rs:538 and execve(candidate) at child.rs:1484 resolve attacker-chosen paths through the live container procfs, with ranikust's whole descriptor table copied in. Fix: resolve the workdir in the parent through the RootPath of / with RESOLVE_NO_MAGICLINKS and fchdir to an O_PATH descriptor in the child. Alternatively, refuse a workdir, argv[0] or PATH entry that resolves through a procfs magic link. Add a T2c regression test (direct_attacks.rs): hold a non-CLOEXEC canary directory descriptor, run a Direct RUN with workdir /proc/self/fd/<n> and with argv[0] /proc/self/fd/<n>, and assert that the RUN fails or that its cwd is not the canary.
- On Linux < 6.3 (5.15 is a measured target), the memfd fallback rustix::fs::memfd_create("ranikust-state", MemfdFlags::CLOEXEC) at anon.rs:214 creates store files with mode 0777 and no exec seal. execve through /proc/self/fd/<n> before exec then passes the permission check, and only the content format stops it. Fix: fchmod(fd, 0600) right after memfd_create, so the exec route gives EACCES whatever the content (0600 is the mode the O_TMPFILE and named ways already use).
- ranikust does not close descriptors it inherited from its launcher (main.rs:94-111 has no close_range). T7's pass in the RUN child only sets close-on-exec (child.rs:1371-1414), and it runs after chdir(workdir). So a non-CLOEXEC directory descriptor passed by the runtime (--preserve-fds, LISTEN_FDS) or leaked by a buggy runtime would be reachable by a Direct RUN through WorkingDir=/proc/self/fd/<n>, even though ranikust is non-dumpable. Fix: close_range(3, ~0U, 0) first in main, before ranikust opens any descriptor of its own.
- rnk-sandbox journal.rs:493-504 and 507-547: replay opens <state>/sandbox/runs/*.journal and *.journal-new without O_NONBLOCK, a regular-file check or a size cap, then read_to_end: a FIFO named *.journal-new blocks the read-only open, a FIFO or /dev/zero-like node named *.journal blocks or grows memory, so start-up hangs every time. Only the state-directory owner can plant one (0700, statedir.rs), so it is not a boundary crossing; open with O_NONBLOCK|O_NOFOLLOW|O_CLOEXEC, require S_ISREG with nlink 1 via fstat, and cap the read (journals are a few KiB).
- rnk-sandbox journal.rs:132-139 vs 493-503: between Journal::create's create_new of <id>.journal-new and its flock, a build starting concurrently on the same state directory can lock and unlink that file in remove_unlocked, so the live build's rename fails ('publish the stub journal') and its RUN fails. Same-principal availability race with a microsecond window; skip *.journal-new entries whose id names a live pid, or create the file already locked (O_TMPFILE plus linkat after flock).
- relay.rs:58 and main.rs:369-371: RUN stdout is relayed to fd 1, the stream that also carries the build's result (the digest, usage.md says 'It prints the image digest on stdout'). The digest stays the last line, but a RUN whose output ends without a newline prefixes that line with attacker text (`tail -n1 | awk '{print $1}'` or `grep -o ... | head -1` then yields the RUN's chosen digest). BuildKit keeps stdout clean; consider relaying RUN stdout to stderr, or at least emitting a newline before the digest when the last relayed byte on fd 1 was not one, and pointing scripts at --digest-file.
- journal.rs:442-451: the doc comment of replay() describes the shared_root branch as live behaviour, but only the #[cfg(test)] Sandbox::start_with_root passes it; stating that it is test-only would keep a future caller from relying on the identity match without the refuse_host_system_dir check done there.
- T20 and ADR-0033 name only rtnl-link-<kind> module autoload as residual; the same rtnetlink path also autoloads traffic-control modules (sch_*, cls_*, act_*, ematch-kind-*) and lwtunnel encaps (rtnl-lwt-*), the most exploited CAP_NET_ADMIN-in-userns surface. Name them in T20 so the residual matches the code.
- The x_tables, conntrack and multicast-routing closures are partial: tc act_ipt/act_xt (still shipped by 5.15 and 6.8) reach x_tables target code, act_ct reaches conntrack, and RTM_NEWROUTE with RTNL_FAMILY_IPMR/IP6MR reaches the multicast routing tables, all via rtnetlink. This is within the ADR's 'every other interface' acceptance; state it in T20.
- The owner rule grants every capability over the netns, not only CAP_NET_ADMIN. Where ranikust lacks CAP_NET_RAW (Podman's default set, or `drop: ALL` plus `add: SYS_ADMIN`), a root RUN on the userns path regains CAP_NET_RAW over its netns (AF_PACKET, SOCK_RAW, IP_TRANSPARENT). ADR-0033 frames the residual as CAP_NET_ADMIN only.
- getsockopt(SOL_IP, SO_IP_SET=83) is gated on CAP_NET_ADMIN over the netns and is not in SOL_IP_REFUSED. It only queries an empty per-netns ipset list, but the seccomp.rs module comment's list of 'options that need CAP_NET_ADMIN over the namespace' is therefore incomplete.
- socket(AF_ALG) stays open in every RUN. BuildKit's vendored moby profile (cd8ee24) now blocks it as unneeded kernel crypto attack surface; a userns_network() addition would cost one instruction.
- Test gaps: the T0 filter test checks unshare(CLONE_NEWUSER) but not a raw clone(CLONE_NEWUSER), and runs only on the CI arch (aarch64 is compile-checked only). The VM smoke netns-check.py runs as root only: it has no non-root USER plus setuid case and no rtnetlink/tc/tunnel-ioctl probes documenting the accepted residual.
- On the userns path every i386/x32/AArch32 syscall gets EPERM, so 32-bit binaries in a --network=none RUN fail outright. This is a compatibility note, not a security finding.
- With the host network, a Full RUN keeps NET_RAW and NET_BIND_SERVICE over the host netns (caps.rs:7-22): it can spoof raw packets on host interfaces and bind free privileged host ports for the RUN's lifetime. T11 accepts sniffing lo only; consider dropping NET_RAW for Network::Host RUNs or stating this in threat-model section 6.
- /proc/net stays readable in a host-network RUN (plan.rs:78-91 matches Docker's list, but Docker's RUN has its own netns): /proc/net/tcp, /proc/net/unix and /proc/net/route disclose the host's listeners, connections and abstract socket names. Masking is only meaningful together with the netns decision.
- No T2 test pins the default RUN's view of host abstract sockets or concurrent builds' loopback; add one with a dummy abstract listener whatever the decision, so a future CLONE_NEWNET/userns change is regression-checked.
- docs/design/sandbox.md:47-49 says the child is created with CLONE_NEWUSER when ranikust lacks CAP_SYS_ADMIN, but clone_flags (spawner.rs:1123-1137) never sets CLONE_NEWUSER; the doc should match the code.
- io_uring_setup/enter/register stay reachable from every Full RUN (Docker's profile denies them). This is generic unprivileged kernel surface that crosses no ranikust boundary. Cover it with the Phase 3 default profile, or list it in threat-model section 6 next to keyrings.
- userfaultfd, perf_event_open and bpf are denied by Docker's profile but only kernel-bounded here (vm.unprivileged_userfaultfd, perf_event_paranoid, unprivileged_bpf_disabled; the RUN lacks CAP_SYS_PTRACE, CAP_PERFMON and CAP_BPF). Document them in the 'Differences from Docker' section of sandbox.md (docs/design/sandbox.md:236-249), which currently omits that RUN has no syscall filter at all.
- threat-model.md:58 and ADR-0003:31-35 describe 'optional seccomp and user namespace' (--seccomp, --userns) that crates/ranikust/src/cli.rs does not parse. clap refuses the flag, so nothing fails open, but the overlay-root strength row overstates the hardening available today.
- Docker-profile denials of kexec_load, init_module/finit_module, iopl/ioperm, open_by_handle_at, syslog, acct, swapon, reboot and settimeofday are covered by the bounding-set drop to Docker's 14 capabilities (crates/rnk-sandbox/src/caps.rs:7-22, bounding_drops). AF_ALG is not denied by Docker's profile either (parity).

### crates/rnk-sched

- rnk-sched Plan::new/chain_deps use linear position() scans per unit and per dependency (crates/rnk-sched/src/scheduler.rs:271-344), O(n^2) in units, and nothing caps the Dockerfile size or stage count (parser caps only line length and depth). About 10^5 chained stages cost seconds to minutes of CPU before any stage runs. Self-limiting because RUN can already burn unbounded CPU. Fix: index units by stage in a Vec<Option<usize>> and cap the stage count.
- Runner::prepare runs for every unit at once (crates/rnk-sched/src/runner.rs:39-44, crates/ranikust/src/build.rs:1144-1194), outside --jobs and the memory gate. It is bounded only by tokio's default 512 blocking threads, and overlay mode also extracts base layers there. Pulls are awaited after a cancel and the registry read_timeout defaults to None (crates/rnk-registry/src/client.rs:89,105), so a slow registry keeps a cancelled build alive. Consider a pull semaphore and a default read timeout.
- RunSlots::new calls tokio Semaphore::new(jobs) (crates/rnk-sched/src/slots.rs:27), which panics (an abort in release) when --jobs exceeds Semaphore::MAX_PERMITS (usize::MAX >> 3). --jobs is unbounded in crates/ranikust/src/cli.rs:374. The flag is operator-trusted; clamp it or validate it in config.
- rnk-metrics write_file follows symlinks in parent components (create_dir_all and dir.join, crates/rnk-metrics/src/report.rs:355-381). At exit it writes to the absolute but non-canonical path (crates/ranikust/src/main.rs:191), while paths_outside_the_root judged the canonical path at start (main.rs:673-740). In kaniko mode on / a symlink component inside the root can be swapped by a base layer or a RUN, which redirects the report inside the container; that is no boundary crossing there. Open the parent directory once at start and use openat/renameat at exit, and consider mode 0600 instead of 0644.
- The cgroup_dir in crates/rnk-metrics/src/resources.rs:186-209 does not refuse '..' components from /proc/self/cgroup, while its sibling crates/rnk-sched/src/memory.rs:189 does. It also reads files with unbounded read_to_string that follows symlinks. The input is kernel-provided, but in a container without /sys mounted, kaniko mode on / would let a RUN or a base layer plant /sys/fs/cgroup files (a FIFO, or a symlink to /dev/zero) that hang or exhaust the end-of-build sample. Align the '..' check, and read with O_NOFOLLOW|O_NONBLOCK and a size cap.
- The panic hook from rnk_metrics::init is process-wide and would run in a cloned RUN child (after pivot_root) if that child ever panicked: it would allocate after a multi-threaded clone and write the report inside the stage root, where the report could land in a layer. Record the pid at init and return early from the hook when getpid() differs.
- The colored log format (the default) prints event messages unescaped (crates/rnk-metrics/src/logfmt.rs colored()), including Dockerfile instruction text and stage names, so terminal control sequences from the Dockerfile reach the operator's terminal. RUN output is relayed raw anyway (relay.rs, peer-owned). Escape control characters in the color format.

### crates/rnk-store

- crates/rnk-store/src/store.rs:987 cleanup takes build ids from tmp/ with no '.lock' filter and no check against register's '<hex>-<hex>-<hex>' format. - Overlay mode does not raise RLIMIT_NOFILE (only kaniko mode does, main.rs:416). On a deep RUN-made tree, delete_contents then stops with EMFILE near the soft limit and leaves the tree with a warning at every start.
- Cache bind mounts get NODEV (and RDONLY for ro) but not NOSUID (crates/rnk-sandbox/src/spawner.rs:1337-1345). A setuid-root or file-capability binary that one build's root RUN leaves in a shared cache runs with Docker's default capabilities in another build's non-root RUN. This stays within T14 and matches BuildKit, but adding MS_NOSUID to cache binds would narrow cross-build cache poisoning.
- warn_if_shared only warns when blobs/, layers/, caches/, locks/ or tmp/ belong to another uid or are group- or other-writable (crates/rnk-store/src/store.rs:1290-1305), and statedir::prepare makes only the state directory and builds/ private. Refusing or tightening these subdirectories too would stop the store from relying on the top-level 0700 alone, for example against a process that kept a descriptor from an earlier, looser set-up.
- Store::publish renames with plain renameat (crates/rnk-store/src/store.rs:1086). Under the per-digest lock no ranikust process can race it, but RENAME_NOREPLACE would turn an unexpected entry that appeared under the name into an error instead of a silent replacement.

- tests/vm/vm.sh:332-339 checks the cloud image only against a SHA256SUMS file fetched over HTTPS from the same origin, without verifying SHA256SUMS.gpg. The downloaded image is then used as a QEMU backing file (vm.sh:517, and vm.sh:575 with RANIKUST_VM_GOLDEN=0) without the self-contained check (no backing-filename, no data-file) that vm.sh:551-555 applies to the golden image. A tampered qcow2 could name a host file as its backing file. Fix: apply the same qemu-img info check to $IMG and verify the signature with Ubuntu's cloud-image key.
- rnk-registry's reqwest and oci-client clients (client.rs:997-1009, 1067-1080) never call no_proxy(), so on Linux HTTP_PROXY, HTTPS_PROXY and ALL_PROXY apply. hyper-util adds no loopback bypass, so when a proxy is set without NO_PROXY, requests to a localhost or 127.0.0.1 registry go to the proxy, and resolve_to_addrs("localhost") no longer applies. T11's claim that localhost resolves to loopback in ranikust's own requests then does not hold. The environment is operator-trusted, so this is a documentation or hardening point: disable the proxy for loopback destinations, or document it.
- deny.toml has no [bans] deny entries, for example aws-lc-rs, aws-lc-sys or openssl-sys. The ADR-0024 choice of ring holds today only because of how features are set (oci-client's default `rustls-tls` would select aws-lc-rs). An explicit ban would make CI enforce it.
- The local and VPS build paths (justfile build-static and test-aarch64, vm.sh zigbuild, lane.sh cargo-zigbuild) use whatever zig and cargo-zigbuild the developer has installed, while CI pins zig 0.16.0 and cargo-zigbuild 0.24.0. The binaries tested at T2 and T2c can therefore come from a different toolchain than CI's. Fix: pin or check the versions.
- Test base images are pulled by mutable tag: alpine:3.20, python:3.13-alpine, ubuntu:24.04 and registry:2 in tests/vm/guest/*.sh, and alpine:3.20 from docker.io in tests/smoke/run-cases.sh:18 and the justfile smoke recipe. tests/container/Dockerfile:4 and tests/registry/compose.yaml:15 already pin by digest. Pinning the others by digest would bind what runs as root in the VM and the T1 lanes.
- CI: whether each action's pinned SHA matches its tag comment, and whether taiki-e/install-action's checksum manifest covers the pinned tool versions, could not be checked offline. Neither is decisive while CI holds no secrets and publishes nothing; check both before a release workflow is added.

### workspace

- crates/ranikust/src/build.rs:734 write_digest_files opens operator digest files with create+truncate, following a final symlink, and runs before the OCI layout, tar and push (build.rs:940). In kaniko mode on / a RUN can plant a symlink to /proc/self/fd/<n> (ranikust's own anonymous blob, truncated before it is written out) or a FIFO (hang after the build) at a volume-held path. Write these files like output.rs write_atomically (O_EXCL temporary + rename, O_NOFOLLOW) and after the outputs.
- crates/ranikust/src/build.rs:631-670 with crates/rnk-registry/src/client.rs:301-319: --skip-tls-verify-pull extends to the push destination whenever the Dockerfile names that registry, and UnverifiedTls carries configured credentials, while plain HTTP withholds them from Dockerfile-chosen registries. Accepted by ADR-0036 and threat-model section 6; consider withholding credentials under UnverifiedTls for registries only --skip-tls-verify-pull covers, mirroring http_credentials.
- crates/rnk-builder/src/layer.rs LayerExporter names build-dir blobs by digest, so identical layers share one file, and crates/rnk-builder/src/upload.rs:330 free removes it by path after its upload; a second BlobLayer of the same digest then relies on the destination fallback (build.rs push path). Reliability only.
- crates/ranikust/src/build.rs:666-667 adds every Dockerfile-named pull registry to skip_tls_verify under --skip-tls-verify-pull. withheld_because (crates/rnk-registry/src/client.rs:318; the test at client.rs:1488 asserts it) then sends configured credentials over unverified TLS to those registries outside kaniko mode on /. Over plain HTTP the same Dockerfile-named registries are deliberately left anonymous (T11: a RUN shares the host network, keeps CAP_NET_RAW and can serve or sniff ports). Consider an unverified_tls_credentials set mirroring http_credentials: only registries the operator typed (--skip-tls-verify-registry, destinations under --skip-tls-verify) get credentials over unverified TLS. Add a regression test that a registry only --skip-tls-verify-pull covers is reached anonymously. ADR-0036 accepts that skipping verification covers the token service; it does not address credentials for Dockerfile-named hosts.
- RANIKUST_DEBUG_FAULT (crates/ranikust/src/main.rs:66,131) is live in release builds. Every value is fail-closed today (panic/error/kernel refusal). Keep it so: add a unit test that any value other than the four known ones changes nothing, so a future value cannot add a bypass.
- The root .gitignore has no generic '*.pem', '*.key', '.env*' or 'credentials' patterns. Nothing sensitive is tracked and the lane outputs are ignored per directory, so this is defence in depth against a stray `git add -A`.
- tests/registry/setup.sh makes server.key 0644 and leaves ca.key at the umask default under tests/registry/_data. The test CA is trusted only through --registry-certificate in tests, so the exposure is limited to local co-users impersonating the loopback test registry. Keeping ca.key 0600 would cost nothing.
